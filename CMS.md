# Edit and publish DigitalTalha

## Connect the editor once

1. Open [Pages CMS](https://app.pagescms.org/) and sign in with GitHub.
2. If asked, install the Pages CMS GitHub App and grant access to **DigitalTalha_website**. Select only that repository.
3. Open the repository and select the **pages-cms** branch for the first review. The branch must be on GitHub for Pages CMS to see it. For future edits, create a branch such as **content/home-updates** from the approved **main** branch, then select it in Pages CMS.

## Edit website content

- **Website pages** has the Home, About, Services, Projects, Blog listing, Contact, policies and 404 copy. **Shared website content** includes the menu, logo, footer, portrait, form copy and process section.
- **Services** contains each service's headline, introduction, artwork, alt text, scope and FAQs. **Portfolio and existing article** contains the hospital case study, screenshots and Meta Ads practice article.
- **Page SEO** has one form per page. Edit its title, description and social image there. Canonical URLs, sitemap links and structured-data relationships are generated by the build. The SEO title automatically ends in “| DigitalTalha”.
- Use **Media** to upload an image, then select it in the relevant image field and provide alt text. Replace an existing service illustration with a similar crop under 100 KB. Upload replacements with a new filename so existing URLs still resolve. Page images and social sharing images have separate fields.
- Saving creates a GitHub change on the branch selected in Pages CMS.

## Write a blog post

Open **Blog posts → Add**. Fill in the headline, excerpt, publication date, body, SEO title and meta description. The editor supports formatting like headings, lists, links and images. Add alt text to any image you insert.

At creation, choose the filename carefully. A file named `marketing-checklist.json` opens at `/blog/marketing-checklist/`. The title can change later while the address stays the same. Each published post automatically gets a square card on `/blog/`, newest first. The card uses the cover image from the post or the site's default design. The existing Meta Ads practice article stays with the portfolio at its original address and has its own editing form.

Leave **Draft** on while writing. Drafts stay out of the generated website, search and sitemap. This GitHub repository is public, so saved draft text and uploaded images can be seen on GitHub. Turn **Draft** off on your review branch when the post is ready to preview. Verify the publication date before merging.

## Preview and go live

1. After saving to **pages-cms** or **content/***, open GitHub **Actions → Website checks and Cloudflare Pages**. The workflow runs checks and supplies a downloadable **offline-website-preview**. With preview credentials configured, the latest successful review appears at [Cloudflare preview](https://pages-cms.digitaltalha-migration.pages.dev/). This address shows the last deployed review branch. Check the run's branch before reviewing.
2. Read the changed pages on mobile and desktop. Check titles, images, links and the blog listing. The Cloudflare preview is noindex, uses an empty sitemap and does not send enquiries.
3. Open a pull request into **main** and merge after reviewing the preview. GitHub runs the checks and automatically publishes the successful build to Cloudflare once the production credentials are configured. Saving or pushing directly to **main** also starts this process. Check the run and the public pages after it finishes.
4. If a release needs to be undone, roll back to the previous verified production deployment in Cloudflare Pages. Revert the source change on GitHub as well if it should be excluded from future builds.

## First-time GitHub deployment setup

The Cloudflare project already exists as a Direct Upload project. Set the GitHub Actions variable `CLOUDFLARE_ACCOUNT_ID` and the secret `CLOUDFLARE_API_TOKEN` for `cloudflare-preview` and `cloudflare-production`. Use a Cloudflare token scoped to Pages Edit for this account. Keep Resend and enquiry settings in Cloudflare. The GitHub workflow only needs the Cloudflare deployment credential.

One-off preview uploads can also use the existing Wrangler login, as described in [Cloudflare Pages](cloudflare/README.md).
